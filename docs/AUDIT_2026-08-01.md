# Acquira — Detailed Technical Audit

**Date:** 2026-08-01
**Branch audited:** `deploy/kubernetes-aws` (75 commits, 1,086 tracked files, working tree dirty with 40+ modified files)
**Scope:** `acquira-{common,core,batch,pdf,ai}`, `frontend/`, `deploy/`, repo root. Excluded `target/`, `node_modules/`.

Five parallel audits were run: backend code quality & architecture, security, frontend, tests & dependencies, and infrastructure & repo hygiene.

---

## Executive summary

The codebase is **substantially better engineered than its surface suggests**. Dynamic SQL is whitelist-guarded, the JWT filter validates tenant access, the AI SQL layer has a real parser and guard, file download paths are traversal-hardened, secrets use `${ENV:default}` with a startup guard, CORS has no wildcard, and card data is masked at the API boundary. The Dockerfiles are multi-stage with pinned base images. There is a genuinely good design-system kit and axios client in the frontend.

The debt is concentrated in five themes:

1. **Two credential/authorization defects that are individually sufficient for full platform compromise** (§1) — a seeded SUPER_ADMIN password re-applied on every production boot, and a missing role-check that lets a tenant admin self-elevate.
2. **~40% of the Java tree is dead code that is still being edited** — the root `src/` tree (231 files, 37,527 lines) is not in any Maven module, yet duplicates live security classes (`JwtUtil`, `TenantContext`, `SecurityConfig`). Plus a 9,362-line unreferenced PDF god class and ~2,255 lines of dead frontend files.
3. **Nothing automated gates production.** No CI of any kind. The documented pre-deployment build runs `-DskipTests`. Four of five modules have zero tests; overall real coverage is 11 test files against 306 built source files.
4. **The service layer has been hollowed out.** 29 of 63 controllers query the database directly; `acquira-core` has 15,757 lines of controller against 4,495 of service. The multi-tenancy backstop exists specifically to compensate.
5. **No migration tooling.** A hand-ordered 40-entry list in `application.properties`, 73 SQL files of which ~33 are orphaned, a 456 KB `schema.sql` re-run on every pod start, no version table, no checksums.

## 1. Security — fix this week

Scored on the tech-debt framework: `Priority = (Impact + Risk) × (6 − Effort)`.

### C1. Seeded SUPER_ADMIN credential, force-reset on every production startup — Priority 45

`acquira-core/src/main/resources/schema.sql:1441` (plus 6 duplicate copies at `:3316`, `:5193`, `:7069`, …) and `data.sql:225`.

The seed inserts user `admin` with a `{noop}`-prefixed plaintext password and `role='ROLE_SUPER_ADMIN'`, then:

```sql
ON CONFLICT (username) DO UPDATE
SET password_hash = EXCLUDED.password_hash, must_change_password = FALSE, role = 'ROLE_SUPER_ADMIN';
```

This is not a one-time seed. The `DO UPDATE` **overwrites whatever password the operator later set**, clears the change-password flag, and re-grants SUPER_ADMIN. `application-prod.properties:56` sets `spring.sql.init.mode=always` and `deploy/k8s/02-configmap.yaml:12` pins `SPRING_SQL_INIT_MODE: "always"` under the `prod` profile — so **every restart re-arms it**. The `{noop}` prefix means the delegating encoder accepts the literal with no hashing.

**Fix:** `ON CONFLICT (username) DO NOTHING`; replace `{noop}` with a bcrypt hash of a generated value; set `must_change_password = TRUE`; add a seeded-admin check to `SecurityStartupGuard` so the `prod` profile refuses to start while the row exists.

### C2. Vertical privilege escalation — a tenant ADMIN can mint SUPER_ADMINs — Priority 40

`acquira-core/.../controller/UserController.java:191-194`, `AdminController.java:88-121`.

`updateUser` is gated `hasAnyRole('ADMIN','SUPER_ADMIN')`. Its own comment claims the role update happens *"only if caller is SUPER_ADMIN"* — but no such check was written:

```java
// GAP-4: Update role (only if provided and caller is SUPER_ADMIN)
if (userDetails.getRole() != null && !userDetails.getRole().isBlank()) {
    user.setRole(userDetails.getRole());
}
```

A bank ADMIN can `PUT /api/users/{ownId}` with `{"role":"ROLE_SUPER_ADMIN"}`. `JwtRequestFilter:208-219` then grants that principal *all* tenants via `getAllTenantIdsCached()` — converting single-tenant admin into full cross-tenant read/write. Both `createUser` methods share the gap and additionally mass-assign `isActive`, `approvalStatus`, and `accountExpiresAt` from `@RequestBody User`.

**Fix:** wrap all three `setRole` call sites in an `isSuperAdmin()` check and reject `ROLE_SUPER_ADMIN` from non-super-admins. Replace `@RequestBody User` with a DTO that omits `role`, `active`, `approvalStatus`.

### H1. AI assistant permits cross-tenant reads — Priority 32

`acquira-ai/.../AiQueryService.java:551-556` (`ensureTenant`), `:594-608` (`validateSql`).

Both guards check for the *presence* of the string `TENANT_ID`, never that the compared value is the caller's tenant:

```java
if (upper.contains("TENANT_ID")) return sql;                          // ensureTenant: trusts the model
if (!upper.contains("TENANT_ID")) return "Missing tenant isolation";  // validateSql
```

The user's free-text question is concatenated into the prompt at `:417`, so a prompt-injection payload ("…filter on tenant_id = 7") produces SQL that passes both guards. Every whitelisted table is tenant-partitioned. `/api/ai` sits under `.anyRequest().authenticated()`, so any logged-in user reaches it. Line 557 also concatenates the id rather than binding it.

**Fix:** after `cleanSql`, regex-scan for `tenant_id\s*(=|IN)` and require every literal to equal `TenantContext.getCurrentTenant()`.

### H2. Row-Level Security backstop is inert — Priority 28

150 × `ENABLE ROW LEVEL SECURITY` in `schema.sql`, but only 3 × `FORCE ROW LEVEL SECURITY` (`db/migration/ALL_MIGRATIONS_CONSOLIDATED.sql:305,310,315`).

PostgreSQL bypasses RLS for the table owner unless `FORCE` is set, and the app connects as the owning role (confirmed by the note in `V2026_07_04_01__api_management_foundation.sql:48`). **147 of 150 policies never apply.** Multiple code comments — including `AiQueryService.java:27,494` — reason as though the backstop is live, which removes the safety net behind H1 and every application-layer tenant filter. `OPTIONAL__force_rls_backstop.sql` exists but is in no `schema-locations` list.

**Fix:** apply that script, or run the app as a non-owner role with DML grants only.

### H3. Default AES-256 master key protects stored secrets, with no prod guard — Priority 32

`acquira-core/src/main/resources/application.properties:329`, `acquira-pdf/.../application.properties:30`, `S3EncryptionService.java:39`, `SecretsEnvironmentPostProcessor.java:156-163`.

`app.encryption.key` falls back to a 32-char literal committed in the repo, and `masterKey()` silently degrades to `DEV_FALLBACK_KEY` with only a `log.warn`. `SecurityStartupGuard` validates `jwt.secret` and the datasource password in `prod` — but **not** this key. A prod deploy that forgets `APP_ENCRYPTION_KEY` encrypts every tenant's S3 secret access key and SMTP password with a key readable from this repository.

**Fix:** add `app.encryption.key` to `SecurityStartupGuard.validateSecurityConfiguration()` with the same fatal-on-prod behaviour as the JWT secret.

### H4 + H5. Trusted-header spoofing defeats IP allowlists, rate limits, and login lockout — Priority 32 (fix as one change)

`ApiKeyAuthFilter.java:263-270` (enforced `:172`), `RateLimitFilter.java:85-91`, `AuthController.java:734-740`.

All three derive the client IP from the leftmost `X-Forwarded-For` hop with no trusted-proxy check, and `server.forward-headers-strategy` is unset. Consequences:

- A stolen API key restricted to a customer egress IP works from anywhere via `X-Forwarded-For: <allowed-ip>`.
- Rotating the header per request defeats the 200/min API limit, the 20/min external limit, the 5/min migration limit, the per-(ip,username) login throttle (`AuthController:139-147`), and the OTP anti-email-bomb limit (`:553-559`).
- `api_request_log.client_ip` (`ApiKeyAuthFilter:220`) is attacker-controlled, poisoning the audit trail.
- `RateLimitFilter.counters` is a `ConcurrentHashMap` keyed on that attacker-controlled string, swept only every 5 minutes — unbounded heap growth from one unauthenticated client.

**Fix:** `server.forward-headers-strategy=NATIVE` plus a single shared trusted-proxy-aware `clientIp()` helper used by all three; cap the `counters` map size. Note `acq-congif.txt` shows nginx sets XFF correctly — the app just doesn't restrict trust to it.

### Verified NOT vulnerable — do not re-audit

- **`deploy/` secrets** — `01-secret.example.yaml` and `docker-compose.yml` hold only self-labelled placeholders. `deploy/.gitignore` correctly excludes the real files.

## 3. No automated gate on production — Priority 40

- **No CI/CD of any kind.** No `.github/`, `Jenkinsfile`, `.gitlab-ci.yml`, `azure-pipelines.yml`, `.circleci/`. Corroborated by the `compile_final_v2..v8.log` series and 24 hand-run `.ps1` scripts at repo root.
- **`TEST_PLAN_PRE_DEPLOYMENT.md` TC-A1 — the build gate that "gates everything else" — is `mvn clean install -DskipTests -T 2C`.** The mandatory pre-deployment build **explicitly disables the test suite.** TC-A5 runs `npm run build` but never `npm run test:run`. Combined with no CI, **effective automated regression coverage at deploy time is zero.**
- The whole document is a manual human checklist (Pass/Fail/Blocked, TC-A1…TC-B6, `psql` snippets). No `junit|vitest|selenium|cypress` references.

## 4. Architecture — the service layer has been hollowed out

### 29 of 63 controllers query the database directly — Priority 24

`acquira-core` has **15,757 lines of controller vs 4,495 of service** — a 3.5:1 inversion. 29 controllers inject `JdbcTemplate`/`EntityManager`; 14 use `@PersistenceContext EntityManager` inside the web layer. Worst offenders:

| Controller | Lines | What lives in the web layer |
|---|---|---|
| `AnalyticsExplorerController` | 1,346 | A full semantic-model query engine: field/measure registries, grain routing, formula parser, aggregation validation, alert evaluation, CRUD |
| `ForecastController` | 944 | The entire forecasting model — run-rate + seasonality clamp, business-day math; 70 SQL-building lines |
| `BusinessController` | 861 | 6 endpoints; `getCeoSummary` spans lines 125-302, `getDashboardKpisFiltered` 551-838; 55 `sql.append(...)` calls |
| `FinanceController` | 697 | — |
| `LeaderboardController` | 574 | — |
| `TopPerformersController` | 347 | — |

Also `TrendsController`, `RevenueKpiController`, `AnalyticsController`, `GroupAnalyticsController`, `CrossFilterController`, `DataExplorerController`.

**This is *why* `TenantConnectionDataSourceConfig` had to be written.** Its own Javadoc (lines 24-31) names `DataExplorerController`, `AnalyticsExplorerController`, `CrossFilterController`, `GroupAnalyticsController`, `ApiKeyController` as endpoints the `TenantAspect` pointcut cannot reach. The tenancy backstop exists to paper over the layering violation.

### `TenantAspect` adds a DB round-trip to every service and repository call — Priority 24

`acquira-common/.../config/TenantAspect.java:23` — the pointcut `execution(* com.acquira..service..*(..)) || execution(* com.acquira..repository..*(..))` matches **every method on every service and every Spring Data repository.** Each invocation does `entityManager.unwrap(Session.class)` + `session.doWork(...)` running `SELECT set_config('app.current_tenant', ?, false)` (lines 44-51).

This forces an EntityManager/connection open even for methods that never touch the DB, and it is **fully redundant** with `TenantConnectionDataSourceConfig`, which stamps the same GUC at pool checkout. That class's Javadoc (line 57) calls the double-set "harmless — same value," which is true for correctness but not for latency, and the cost multiplies on nested service→repository chains.

### `BusinessController` reads the tenant id straight off the client header — Priority 32

Lines **43, 125, 305, 552, 841**: `@RequestHeader("X-Tenant-Id") Long tenantId`, passed unvalidated into `activityRepository.countByTenantIdAndStatusAndCalcDate(...)` and native queries. `JwtRequestFilter:139-159` *does* validate the same header against `UserTenantAccess` — but on failure it only logs a warning (line 149) and falls back to the default tenant in `TenantContext`; **the raw header value still reaches the controller parameter unchecked.** This is the only place in the codebase using this pattern, and it defeats the entire tenancy design.

### Nullable-tenant "backward-compatible" overloads — Priority 32

`VolumeRevenueRepository` lines 19/28, 199/207, 321/330, 600/623, 749/768, 972/976, 1173/1272, 1465/1473, 1600/1609, 1773/1969 — **10 method pairs** where the 1-arg overload delegates with `tenantId = null`, and `null` means *emit no tenant predicate* (line 78: `if (tenantId != null) sql.append("AND s.tenant_id = :tenantId ")`). Same shape at `ExecutiveDashboardRepository.java:150-159`. **Calling the wrong overload silently returns every tenant's data.** Delete the unscoped variants.

Related: `PdfController.java:327` still calls the 3-arg `coreClient.fetchInsights(mid, year, month)`, explicitly `@Deprecated` in `CoreServiceClient.java:33` as *"Unscoped — does not verify the merchant belongs to the caller's tenant."* Lines 1027 and 1074 use the safe 4-arg form; 327 was missed.

### Other architecture findings

- **`VolumeRevenueRepository` — 2,132 lines, 291 `sql.append` calls, 50 methods, nine distinct reports in one class.** Values are bound so injection risk is low, but it is untestable and every report change edits the same file.
- **Tenant-resolution helper copy-pasted 11 times** with 4 names (`tenant()`, `getTenantId()`, `tenantId()`) and 3 exception types across `CrossFilterController:44`, `DataExplorerController:64`, `EmailController:61`, `EmailSmtpController:43`, `LeaderboardController:33`, `ReportFilterController:20`, `SalesAgentProfileController:25`, `SalesCountryLeadController:25`, `SalesPortfolioController:53`, `SavedFilterController:21,36`. `SalesTeamController:21` delegates to a `TenantService` the other ten ignore. 128 total `TenantContext.getCurrentTenant()` call sites. Numeric coercion helpers (`bd`, `lng`, `dbl`) duplicated the same way across 5 files.
- **Controllers mutate global `TenantContext` and `clear()` it mid-request** — `PdfController.java:307-312,326-330,475` clears the tenant in a `finally` **on the servlet request thread**, so any later tenant-scoped call in the same request hits `TenantContext.getVisibleTenants()` which throws by design (`TenantContext.java:57`). Should save-and-restore. `EmailController.java:230-245` does the same on a hand-rolled daemon thread spawned inside a controller.
- **`CoreServiceClient`** (`acquira-pdf/.../controller/`) — `@Autowired(required = false)` on `MerchantInsightService`, then branches at line 45 between an in-JVM call and `RestTemplate` HTTP. Two entirely different execution paths (transaction semantics, error handling, tenant propagation) selected by classpath accident. `new RestTemplate()` at line 28 bypasses Spring config — no timeouts, no interceptors. A `@Service` misfiled in a `controller` package.
- **Each library module declares itself a Spring Boot app** — `BatchApplication`, `PdfApplication`, `AiApplication` are all `@SpringBootApplication`, while `CoreApplication:11` component-scans all five packages. Scanning a package with a nested `@SpringBootConfiguration` re-registers `@EnableAutoConfiguration` and an implicit second scan from each. Pick one model.
- **The circular-dep fix widened the base instead of extracting interfaces.** `fix-circular.ps1` bulk-moved `MerchantInsightService`, `MerchantMetricCalculator`, `MetricCalculatorService`, `AuditService` into `acquira-common`, which is now the **largest module at 175 files** — a "shared kernel" holding core domain logic. The POM graph is acyclic; the conceptual cycle is not resolved.

### Error handling

- **53 empty catch blocks across 28 files, used deliberately as control flow.** Worst: `ExecutiveDashboardRepository.java:165-169,189,205-208` — nine `try { q.setParameter(...) } catch (Exception e) {}`, self-described at line 164 as a *"robustness hack for dynamic queries."* Binding failures are invisible; the enclosing `catch` then returns `0`/empty, **so a broken dashboard query renders as a legitimate zero.** Also `PlaywrightPdfService` (9), `TransactionJobConfig` (5), `AiQueryService` (5), `IntegrationPullService:738-741` (4 chained). `ChurnScoringService.java:288,384,478` catches **`Throwable`**.
- **588 `catch (Exception ...)` blocks**, and `GlobalExceptionHandler` is bypassed by ~30 controller methods that hand-roll a `ResponseEntity`, so error shape and status differ per endpoint. 61 bare `throw new RuntimeException(...)`; no typed exception hierarchy.
- **17 `System.out.println` in production paths** — `ExcelSplitterTasklet` (6), `VolumeRevenueRepository` (4, in a `@Repository`), `MerchantController` (1).

### Lower-severity backend items
